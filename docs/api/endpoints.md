# BLENDi Pulse API — Endpoint Reference

BLENDi Pulse API follows a REST-style design and returns JSON for application endpoints, with one redirect-based OAuth callback flow. Authentication-protected routes use JWT Bearer tokens sent in the `Authorization` header as `Bearer <accessToken>`. Successful application responses use `success: true`, while error responses use `success: false` plus a stable machine-readable `code` and an English `message`. Development base URL is `http://localhost:3000`. The production base URL will be defined after the Railway deployment configuration is finalized.

> Exceptions: `GET /ping` returns a plain JSON health payload without the `success` envelope, and `GET /auth/google/callback` returns an HTTP redirect to the mobile deep link instead of JSON.

---

## Base Conventions

### Authorization Header

```http
Authorization: Bearer <accessToken>
```

### Content Type

```http
Content-Type: application/json
Accept: application/json
```

### Body Nesting Limit

On every route that parses a JSON or urlencoded body (including the 4 MB routes), a body nested deeper than **32 levels** (each object or array counts as one) is rejected before reaching the route:

```json
{ "success": false, "code": "validation/invalid-input", "message": "Request body is nested too deeply." }
```

Status `400`. No legitimate request is close to this limit (the deepest is 3 levels). The RevenueCat webhook reads its raw body and is not affected.

### Message Format

The API returns a stable top-level error `code` such as `auth/invalid-credentials` together with an English `message`. When validation fails, the nested `errors` array still uses field-level messages generated by the shared Zod schemas, which may be i18n-style keys such as `errors.validation.required`.

## Authentication

### POST /auth/register

Creates a new user account and returns the initial session tokens.

**JWT required:** No

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `email` | string | Yes | Valid email address, normalized to lowercase |
| `password` | string | Yes | Minimum 8 characters, maximum 72, must include uppercase, lowercase, and a digit |
| `name` | string | Yes | 2 to 60 characters |
| `blendiModel` | string | Yes | One of `Lite`, `ProPlus`, `Steel` |
| `goal` | string | Yes | One of `Muscle`, `Wellness`, `Energy`, `Recovery` |
| `preferredLanguage` | string | No | One of `en`, `pt-BR`; defaults to `en` when omitted |
| `dailyProteinTarget` | number | Yes | Integer between 10 and 800 |
| `dailyCalorieTarget` | number | Yes | Integer between 300 and 15000 |
| `timezone` | string | Yes | IANA timezone string such as `America/Sao_Paulo` |

**Success response**

**Status:** `201 Created`

```json
{
  "success": true,
  "data": {
    "user": {
      "id": "string",
      "email": "string",
      "name": "string",
      "blendiModel": "Lite | ProPlus | Steel",
      "blendiOwnership": "blendi | other | none",
      "otherBlenderModel": null,
      "dietaryPreferences": [],
      "goal": "Muscle | Wellness | Energy | Recovery",
      "locale": "en | pt-BR",
      "unitSystem": "metric | imperial",
      "timezone": "string",
      "dailyProteinTarget": 150,
      "dailyCalorieTarget": 2000,
      "dailyCarbTarget": 200,
      "dailyFatTarget": 67,
      "longestStreak": 0,
      "createdAt": "2026-04-29T12:34:56.000Z"
    },
    "accessToken": "string",
    "refreshToken": "string"
  }
}
```

`blendiOwnership`, `otherBlenderModel` and `dietaryPreferences` are **not** accepted at registration (the Zod schema strips them) — a new account always starts as `blendiOwnership: "blendi"`, `otherBlenderModel: null`, `dietaryPreferences: []`, and the real values are collected by the onboarding and saved through `PATCH /users/me`. They are returned here (and in every other endpoint that returns the full user, see `GET /users/me`) so the client never has to guess their defaults.

`dailyFatTarget` is derived automatically from `dailyCalorieTarget` (30% of calories, converted to grams) at account creation — it is never part of the request body. The body-composition profile fields collected later in the onboarding flow (`weightGoal`, `activityLevel`, `targetWeight`, `birthDate`, `biologicalSex`) are **not** part of registration: they are not accepted in this request body and are not present in this response. The account is created with internal placeholder defaults for them, which are overwritten by the first real `PATCH /users/me` that completes the onboarding body step (see `completingBodyOnboarding` under `PATCH /users/me` below).

**Status codes**

| Status | Meaning |
|---|---|
| `201` | User created successfully |
| `400` | Request body failed Zod validation |
| `409` | Email already exists |
| `500` | Unexpected server error |

### Google sign-in flow (one-time code + verifier)

Since CP-1.1.1d the Google callback never puts tokens or user data in the deep link. The app proves it started the flow with a PKCE-style verifier (RFC 7636, `S256`):

1. The app generates a random **verifier** (32 bytes, base64url) and keeps it in memory only. The **challenge** is `base64url(SHA-256(verifier))` (43 chars, no padding).
2. `GET /auth/google/url?codeChallenge=<challenge>` → the backend signs the challenge into the `state` JWT and returns the Google URL.
3. The app opens the URL with `WebBrowser.openAuthSessionAsync`. After the user authorizes, Google calls `GET /auth/google/callback`; the backend resolves the user (login, link or create) and redirects to `blendipulse://auth/callback?code=<one-time code>`.
4. The app calls `POST /auth/google/exchange` with `{ code, codeVerifier }` and receives the session.

The one-time code is 32 random bytes (base64url). Only its SHA-256 hash is stored (`googleauthcodes` collection), bound to the user, the challenge from the state and `isNewUser`, with a 2-minute expiry removed by a MongoDB TTL index. A code intercepted from the deep link (for example by another Android app registering the `blendipulse://` scheme) is useless without the verifier.

### GET /auth/google/url

Returns the Google OAuth authorization URL that the mobile app must open using `expo-web-browser`.

**JWT required:** No

**Query parameters**

| Field | Type | Required | Notes |
|---|---|---|---|
| `codeChallenge` | string | Yes | `base64url(SHA-256(codeVerifier))`, exactly 43 chars `[A-Za-z0-9_-]`. Stored inside the signed `state` JWT (`{ csrf: true, codeChallenge }`, 10 min) |

**Success response**

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "url": "https://accounts.google.com/o/oauth2/v2/auth?..."
  }
}
```

**Status codes**

| Status | Meaning |
|---|---|
| `200` | Authorization URL generated successfully |
| `400` | `codeChallenge` missing or not in the expected format (`validation/invalid-input`) |
| `500` | Unexpected server error |

### GET /auth/google/callback

Google OAuth callback endpoint. This endpoint is called by Google after the user authorizes access and is not meant to be called directly by the mobile client.

The backend validates the callback (including the challenge inside `state`), exchanges the authorization code with Google, logs the user in, links the Google account, or creates a new account when needed, and then redirects the browser to the mobile deep link with a one-time code.

**JWT required:** No

**Query parameters**

| Field | Type | Required | Notes |
|---|---|---|---|
| `code` | string | Usually yes | Authorization code returned by Google |
| `state` | string | Yes | CSRF protection token originally issued by `GET /auth/google/url`; a short-lived JWT signed by the backend carrying the PKCE challenge. A `state` without a valid challenge is rejected as `invalid_state` |
| `error` | string | No | Present when the user cancels or Google returns an auth error |

**Success behavior**

**Status:** `302 Found`

Redirects to:

```text
blendipulse://auth/callback?code=<one-time code>
```

No access token, refresh token or user data is ever placed in this URL. The app exchanges the code with `POST /auth/google/exchange`.

**Error behavior**

Handled OAuth failures also return a redirect instead of JSON. The backend redirects with an i18n error key:

```text
blendipulse://auth/callback?error=errors.auth.google_auth_failed
```

Possible error keys include `errors.auth.google_cancelled`, `errors.auth.invalid_state`, `errors.validation.required`, `errors.auth.email_not_verified`, `errors.auth.google_account_conflict` and `errors.auth.google_auth_failed`.

**Status codes**

| Status | Meaning |
|---|---|
| `302` | Redirect to the mobile deep link after successful or handled failed OAuth flow |
| `500` | Unexpected server error |

### POST /auth/google/exchange

Exchanges the one-time code from the Google deep link, plus the verifier, for the session. Rate limited with the same limiter as `POST /auth/login` (10 failed requests per 15 minutes per IP; successful exchanges do not count).

**JWT required:** No

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `code` | string | Yes | One-time code from `blendipulse://auth/callback?code=...` (43 chars base64url) |
| `codeVerifier` | string | Yes | The verifier whose SHA-256 was sent as `codeChallenge` (43–128 chars base64url) |

The code is consumed atomically on lookup — it works **once**, even when the verifier check fails afterwards, so a wrong attempt also burns it. The verifier is compared against the stored challenge in constant time.

**Success response**

**Status:** `200 OK`

Same shape as `POST /auth/login`, plus `isNewUser` (as in `POST /auth/apple`). `user` is the full profile, serialized exactly like `GET /users/me` (note `preferredLanguage` instead of `locale`).

```json
{
  "success": true,
  "data": {
    "user": { "id": "...", "email": "...", "preferredLanguage": "en", "...": "same fields as GET /users/me" },
    "accessToken": "<jwt>",
    "refreshToken": "<jwt>",
    "isNewUser": false
  }
}
```

**Error response**

Every failure — malformed body, unknown code, code already used, expired code, wrong verifier, or the user deleted in the meantime — returns the same generic response, without the reason:

```json
{
  "success": false,
  "code": "auth/google-exchange-failed",
  "message": "Google sign-in could not be completed. Please try again."
}
```

**Status codes**

| Status | Meaning |
|---|---|
| `200` | Code and verifier accepted; session issued |
| `401` | Generic failure (`auth/google-exchange-failed`) |
| `429` | Too many failed attempts (`auth/too-many-requests`) |
| `500` | Unexpected server error |

### POST /auth/forgot-password

Starts the password reset flow by generating an OTP and attempting to send it by email.

**JWT required:** No

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `email` | string | Yes | Valid email address |

**Success response**

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "message": "errors.auth.forgot_password_sent"
```

### POST /auth/verify-otp

Validates the six-digit OTP sent by email and returns a temporary password reset token.

**JWT required:** No

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `email` | string | Yes | Valid email address |

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
```

### PATCH /auth/reset-password

**JWT required:** No

**Request body**

| Field | Type | Required | Notes |

**Success response**

**Status:** `200 OK`

| Status | Meaning |

### PATCH /users/me

Partially updates the authenticated user's profile and goals.

**JWT required:** Yes

**Request body**

All fields are optional. The endpoint only updates fields that are present in the request body.

| Field | Type | Required | Notes |
|---|---|---|---|
| `blendiModel` | string | No | One of `Lite`, `ProPlus`, `Steel`. Sent **without** `blendiOwnership` it means "I have a real BLENDi" — see *Blender ownership rules* below |
| `blendiOwnership` | string | No | One of `blendi`, `other` (older model or another brand), `none` (no BLENDi yet) — see *Blender ownership rules* below |
| `otherBlenderModel` | string | No | Free text with brand/model for `blendiOwnership: "other"`. Control characters (including line breaks and bidi overrides) are replaced by a space, then the text is trimmed; at most 60 characters after trimming (`errors.validation.too_long`); an empty/blank string clears the field. Never sent to the AI, to analytics or to logs |
| `dietaryPreferences` | string[] | No | At most 16 items, each one of `dairy_free`, `vegan`, `nut_free`, `no_added_sugar`; duplicates are removed (order of first occurrence is kept); `[]` means "no restrictions". Unknown value, wrong type or more than 16 items → `400` with a single `errors.validation.invalid_option` issue. Applied by the Pulse AI and Pantry Scanner prompts (see those endpoints) |
| `goal` | string | No | One of `Muscle`, `Wellness`, `Energy`, `Recovery` |
| `weightGoal` | string | No | One of `lose`, `maintain`, `gain` — weight direction goal, independent of `goal`; triggers an automatic recalculation of `dailyProteinTarget`/`dailyCalorieTarget`/`dailyCarbTarget`/`dailyFatTarget` (see below) |
| `dailyProteinTarget` | number | No | Integer between 10 and 800 |
| `dailyCarbTarget` | number | No | Integer between 0 and 1500 |
| `dailyCalorieTarget` | number | No | Integer between 300 and 15000 |
| `dailyFatTarget` | number | No | Integer between 0 and 600 |
| `dailyHydrationTarget` | number | No | Integer between 500 and 8000 (millilitres; `DAILY_HYDRATION_TARGET_MIN`/`MAX` in `packages/shared`) |
| `weight` | number | No | Number between 20 and 300 (kg) — current body weight; also triggers the automatic macro recalculation above and, when different from the previously saved value, appends an entry to `weightHistory` (see `GET /users/me/weight-history`) |
| `height` | number | No | Number between 100 and 250 (cm) — also triggers the automatic macro recalculation above |
| `targetWeight` | number | No | Number between 20 and 300 (kg) — goal weight, independent of `weight`; when present together with `weight`/`weightGoal`, the response includes a `weightTargetEta` prediction (see below) |
| `activityLevel` | string | No | One of `sedentary`, `lightlyActive`, `moderatelyActive`, `veryActive`, `extremelyActive` — also triggers the automatic macro recalculation above |
| `birthDate` | string | No | ISO 8601 date (`YYYY-MM-DD`); must resolve to a plausible age between 13 and 120 years; also triggers the automatic macro recalculation above |
| `biologicalSex` | string | No | One of `male`, `female` — also triggers the automatic macro recalculation above |
| `completingBodyOnboarding` | boolean | No | Must be exactly `true` when present; transient signal (never persisted as-is) that marks this specific PATCH as the real onboarding body-step completion — this is the only way the backend sets `hasRealBodyProfile: true` |
| `preferredLanguage` | string | No | One of `en`, `pt-BR`; stored internally as `locale` |
| `unitSystem` | string | No | One of `metric`, `imperial` |

When the body includes `weight`, `height`, `activityLevel`, `weightGoal`, `birthDate`, `biologicalSex`, or `goal`, and the user's profile has all of weight/height/birthDate/biologicalSex/activityLevel/weightGoal/goal available (merging this request's values with whatever is already saved), the backend recalculates `dailyProteinTarget`, `dailyCalorieTarget`, `dailyCarbTarget`, and `dailyFatTarget` from scratch (same Mifflin-St Jeor formula as `POST /users/calculate-macros`) and that recalculated value **overrides** any `dailyProteinTarget`/`dailyCalorieTarget`/`dailyCarbTarget`/`dailyFatTarget` sent in the same request body.

#### Manual macro-edit warnings (`warnings`)

When a request is a **pure manual edit** of the macro targets — it includes at least one of `dailyProteinTarget`, `dailyCalorieTarget`, `dailyCarbTarget` or `dailyFatTarget` and **no** automatic recalculation ran for it (none of the triggers above was in the body) — the backend compares each edited value with sensible ranges and, when one falls outside, adds a `warnings` array to `data.user`. The values are **saved anyway**: a warning never blocks the update and never changes the status code.

```json
"warnings": [
  {
    "field": "dailyProteinTarget",
    "code": "macros/protein-above-range",
    "message": "warnings.manualMacroEdit.proteinAboveRange"
  }
]
```

| `code` | `field` | Raised when (strict comparisons — the boundary value itself does **not** warn) |
|---|---|---|
| `macros/protein-below-range` | `dailyProteinTarget` | `dailyProteinTarget / weight < 0.8` g/kg |
| `macros/protein-above-range` | `dailyProteinTarget` | `dailyProteinTarget / weight > 3.5` g/kg |
| `macros/calories-below-bmr` | `dailyCalorieTarget` | `dailyCalorieTarget <` the user's BMR |
| `macros/calories-above-tdee` | `dailyCalorieTarget` | `dailyCalorieTarget > 1.6 ×` the user's TDEE |
| `macros/carb-below-range` | `dailyCarbTarget` | `dailyCarbTarget / weight < 0.5` g/kg |
| `macros/carb-above-range` | `dailyCarbTarget` | `dailyCarbTarget / weight > 8` g/kg |
| `macros/fat-below-range` | `dailyFatTarget` | `dailyFatTarget / weight < 0.5` g/kg |
| `macros/fat-above-range` | `dailyFatTarget` | `dailyFatTarget / weight > 2` g/kg |

- Only the fields **present in the request** are evaluated, and at most one warning per field is returned (the `below` and `above` codes are mutually exclusive). Three out-of-range targets in the same request yield three warnings.
- `weight` is the weight **already saved** for the user; the calorie rules also need the saved height, birth date, sex and activity level (BMR/TDEE). An account that skipped the onboarding body step has none of that, so it never receives a warning — verified live by the CP-1.1.1b pentest.
- If the body contains an automatic-recalculation trigger (`weight`, `height`, `activityLevel`, `weightGoal`, `birthDate`, `biologicalSex` or `goal`), the targets sent in the same request are overwritten by the recalculated values and **no `warnings` are returned** — each of the seven triggers was checked on its own. Sending only `dailyHydrationTarget` and/or `dietaryPreferences` never recalculates and never warns.
- `warnings` and `imc`/`imcUnit`/`imcClassification` are mutually exclusive; `warnings` and `weightTargetEta` can appear together (CP-A.2.1).
- `message` is an internal translation key, **not** user-facing text. Clients must translate by `code`: the mobile app maps each known `code` to a typed translation key (`apps/mobile/src/utils/nutritionGoals.utils.ts`), shows the text next to the field named in `field`, and ignores any `code` it does not know (including the two `fat` codes while the fat target is hidden in the UI).

#### Blender ownership rules

Enforced by the backend (`apps/api/src/utils/blenderOwnership.utils.ts`), never trusting the app to send a consistent payload. The two new ownership options store `blendiModel: "Lite"` — the enum is **not** extended and `BLENDER_LIMITS` (volume/protein caps used by the AI guardrail) is unchanged, so an `other`/`none` user always gets the most conservative limits.

| Request | Stored result |
|---|---|
| `blendiOwnership: "other"` or `"none"`, any `blendiModel` | `blendiModel` is always `"Lite"` (a `Steel` sent in the same PATCH is overridden) |
| `blendiOwnership: "blendi"` or `"none"` | `otherBlenderModel` is cleared, even if text was sent |
| `blendiOwnership: "other"` + `otherBlenderModel: "Ninja"` | text trimmed and saved; `"other"` without text keeps the saved text; blank text clears it |
| `blendiModel` without `blendiOwnership` | the user picked a real BLENDi: `blendiOwnership` becomes `"blendi"` and `otherBlenderModel` is cleared |
| `otherBlenderModel` alone | saved only if the account is currently `"other"`, silently ignored otherwise |

The "text alone" write is a conditional update (`{ blendiOwnership: "other" }` in the filter) so a concurrent PATCH that switches the ownership can never leave orphan text behind — found by the CP-1.1.1a pentest and covered by an exhaustive interleaving test. `blendiModel` is **not** a macro-recalculation trigger.

Changing the diet or the model does not touch `AiCache` entries by itself: the diet is part of the cache key, so a different diet simply misses the old entries (the Me screen additionally calls `DELETE /pulse-ai/cache` after a model change).

**Behavior confirmed by the CP-1.1.1b pentest** (live, against the real API): every limit above is inclusive and exact at the boundary (e.g. `dailyProteinTarget` 10 and 800 are accepted, 9 and 801 are rejected); numbers sent as strings, fractions, `null`, booleans, arrays, objects, `Infinity`, `-Infinity`, negative values and MongoDB operators (`{"$gt":0}`, `{"$ne":null}`, `{"$inc":5}`) are rejected with `400`, while JSON integers written as `150.0` or `1.5e2` are accepted as `150`; keys that are not part of the schema (`isPro`, `totalXP`, `email`, `password`, `role`, `_id`, `$set`, `__proto__`…) are silently dropped and answered with `200`, never applied; the account is always the one in the token (an `_id`/`id`/`userId` in the body has no effect); concurrent requests that touch different fields never lose an update. ## Pulse AI

### POST /pulse-ai/chat

Generates a structured Pulse AI recipe for the authenticated user.

**JWT required:** Yes

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `message` | string | Yes | 1 to 500 characters |
| `language` | string | No | One of `en`, `pt-BR`; when present, overrides the profile language for this request |

The `language` field has priority over the user's stored `preferredLanguage` / `locale`. This override affects prompt generation, cache key generation, and the response content.

**Processing pipeline**

1. Validates the request body against `pulseAiChatSchema`.
2. Loads the authenticated user's Pulse AI profile and resets daily usage if the user's local day has changed.
3. Reserves usage atomically for non-Pro users with `findOneAndUpdate` and `dailyAiUsage: { $lt: 3 }`.
4. Normalizes the message, generates a MongoDB cache key using user context (including the user's `dietaryPreferences`, normalized and order-independent) plus `AI_PROVIDER` and `AI_MODEL`, and checks the `AiCache` collection. Because the diet is part of the key, changing it never returns a recipe generated under the previous diet, and returning to the same diet reuses the original entry.
5. On a cache hit, returns the cached recipe immediately with `fromCache: true` and the remaining daily quota.
6. On a cache miss, fetches the last 5 blend recipe names for prompt context.
7. Builds the final prompt through `promptBuilder.service`, personalizing it with the user's `blendiModel` (physical blender guardrails — power/protein limits per model), `goal` (Muscle/Wellness/Energy/Recovery), `weightGoal` (lose/maintain/gain — adds explicit calorie/recipe bias guidance for the chosen weight direction) and `dietaryPreferences` (see *Dietary restrictions in the prompt* below) in addition to macro targets, unit system, and recent blend history. The free-text `otherBlenderModel` is never read by this endpoint.
8. Calls the configured AI provider abstraction, which is selected at runtime through `AI_PROVIDER`, `AI_MODEL`, and `AI_API_KEY`.
9. Parses the returned JSON and validates it against `pulseAiRecipeSchema`; if the first response is invalid JSON, the backend retries once with a strict JSON-only instruction.
10. Persists the validated recipe in MongoDB cache and returns it with `fromCache: false` and `usageRemaining`.

**Success response**

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "recipe": {
      "title": "Berry Blast",
      "ingredients": [
        {
          "name": "Blueberries",
          "amount": "100 g"
        }
      ],
      "macros": {
        "protein": 30,
        "carbs": 22,
        "fat": 6,
        "calories": 280
      },
      "prepTimeSeconds": 60,
      "blendInstruction": "Blend for 45 seconds.",
      "tip": "Use frozen fruit for a thicker texture.",
      "hasSubstitutes": false,
      "steps": [
        { "text": "Add the blueberries and yogurt to the cup." },
        { "text": "Add the frozen banana and pulse to break it up.", "pulseCount": 6 },
        { "text": "Blend on high for 45 seconds until smooth." }
      ]
    },
    "fromCache": false,
    "usageRemaining": 2,
    "aiProvider": "google",
    "aiModel": "gemini-2.5-flash-lite",
    "xpAwarded": 3,
    "conversationId": "string",
    "macrosValidated": true
  }
}
```

`xpAwarded` is the multi-occurrence Pulse AI usage XP. It is returned for both cache hits and fresh generations after a successful request.

`conversationId` is the `_id` of the `Conversation` document the message was saved to. `macrosValidated` indicates whether the recipe's declared macros passed mathematical validation against its ingredients — it is `false` when the discrepancy exceeds 15% even after the automatic retry. A `macrosValidated: false` response does not block the recipe from being returned; it is only an indicator of reduced accuracy.

#### Dietary restrictions in the prompt

When the user has at least one of `dairy_free`, `vegan`, `nut_free` or `no_added_sugar`, the system prompt gets a **"Dietary restrictions (mandatory)"** block (English, like the rest of the prompt) placed after the weight-goal guidance and before the physical blender guardrails, which stay last. An account with no preference (or an old account without the field) gets a byte-identical prompt to before. The block:

- treats every restriction as a hard requirement and states that it takes priority over any ingredient mentioned elsewhere in the prompt;
- states that the restrictions can never be waived, lifted or overridden by the user message (claims of medical clearance, "ignore previous instructions", text imitating a system message or closing tag) — when asked, the recipe keeps the restriction and the `tip` explains the substitution (`hasSubstitutes: true`);
- lists per-diet rules: `nut_free` (no peanuts or tree nuts nor derivatives; listed first because it is usually an allergy), `vegan` (no animal-origin ingredient; protein powder must be plant-based), `dairy_free`, `no_added_sugar` (natural fruit sugar is allowed).

With a diet active, the fixed parts of the prompt also stop *suggesting* ingredients that violate it: the nutrition reference table omits them (a new table entry must be classified in `NUTRITION_ENTRY_RESTRICTIONS`, enforced by a test), the unit example uses `water` instead of `almond milk`, the `gain` guidance and the Lite/Steel hardware hints drop the conflicting examples. This was needed because the pentest showed the explicit priority clause alone still let `Unsweetened almond milk` through for `nut_free` users (2 of 12 generations) — the prompt itself was offering it.

The diet is enforced **by the prompt only**: there is no ingredient validation on the backend, so compliance is probabilistic (see `docs/fixes/cp-1.1.1a-testes-pentest.md` for measured numbers and residual risk). The diet is not editable in the Me screen yet (CP-1.1.1b).

`steps` is an optional array of structured preparation steps (`text`, and `pulseCount` when the step involves adding ice or frozen fruit) requested from the AI alongside `blendInstruction`; it may be absent on recipes generated before this field existed.

## Pantry Scanner

### POST /pantry-scanner/analyze

Analyzes a pantry image, filters low-confidence ingredients, and generates up to two Pulse AI recipes from the usable ingredients.

**JWT required:** Yes

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `imageBase64` | string | Yes | Base64 image payload with an effective maximum size of approximately 2 MB |
| `mimeType` | string | Yes | One of `image/jpeg` or `image/png` |

**Processing pipeline**

1. Validates the request body with `pantryScanSchema` and calculates the image size in KB for structured logging.
2. Loads the authenticated user and checks `isPro`; Pro users skip the free-tier monthly limit gate.
3. For free-tier users, if `Date.now() > scanResetDate`, resets `scanCount` to `0` and recalculates `scanResetDate` with `addMonths(previousScanResetDate, 1)`, preserving the original billing cycle anchor.
4. If the current free-tier `scanCount >= 3`, returns `429 Too Many Requests` with code `scanner/monthly-limit-reached` plus `scansUsed`, `scansLimit`, and `resetDate`.
5. Calls `callVisionAi` with the pantry-analysis prompt built by `pantryPromptBuilder.service.ts`.
6. Parses and validates the returned JSON; if `noFoodDetected: true`, returns `200 OK` with empty arrays and does not increment the scanner.
7. Filters the detected ingredients to confidence levels `high` and `medium`; if the filtered array becomes empty, returns `200 OK` with `noUsableIngredients: true` and does not increment the scanner.
8. Only after valid ingredients are confirmed, increments `scanCount` atomically with `$inc`, then generates recipes through `promptBuilder.service.ts` (the same internal prompt function as Pulse AI, so the user's `dietaryPreferences` produce the same "Dietary restrictions (mandatory)" block — see `POST /pulse-ai/chat`) and returns the Pantry Scanner XP payload.

With a diet active, ingredients detected in the photo that violate it are treated by the prompt as unavailable (the recipes are built from the compliant remaining ones, and the list is empty only when fewer than 2 distinct compliant recipes are possible), and ingredient names are declared to be data, never instructions. The backend does not filter ingredients by name.

### POST /webhooks/revenuecat/{REVENUECAT_WEBHOOK_PATH_SECRET}

Receives subscription lifecycle events from RevenueCat and synchronizes the corresponding user's subscription state. This endpoint is public and called directly by RevenueCat, not by the mobile client. It is mounted before the global JSON body parser and reads the raw request body.

**Unpredictable path.** The last path segment is the value of the required `REVENUECAT_WEBHOOK_PATH_SECRET` environment variable (at least 32 characters, `[A-Za-z0-9_-]` only; generate with `openssl rand -hex 32`). The API refuses to start without it. Only the exact path matches: the old fixed `/webhooks/revenuecat`, sub-paths, a trailing slash and different letter case all return the global `404`. This is an extra layer against automated scanners — the real protection is the `Authorization` header check below. The full URL (including this segment) is what must be configured in the RevenueCat dashboard.

**JWT required:** No

**Request headers**

| Field | Type | Required | Notes |
|---|---|---|---|
| `Authorization` | string | Yes | Static value configured in the dashboard's "Authorization header value" field (HMAC signing is off). Compared in constant time against `REVENUECAT_WEBHOOK_SECRET`; it must match exactly, including the `Bearer ` prefix if the dashboard value has one |

**Request body**

The payload follows RevenueCat's webhook event schema. Relevant fields:

| Field | Type | Required | Notes |
|---|---|---|---|
| `event.id` | string | Yes | RevenueCat event identifier |
| `event.type` | string | Yes | Only `INITIAL_PURCHASE`, `RENEWAL`, `CANCELLATION`, and `EXPIRATION` are processed; other types are acknowledged and ignored |
| `event.app_user_id` | string | Yes | RevenueCat app user id, matched against the local user by `_id` or `revenueCatCustomerId` |
| `event.app_id` | string | No | Must be one of the comma-separated ids in `REVENUECAT_APP_IDS` (one per platform; the legacy `REVENUECAT_APP_ID` is also accepted); events from other apps are ignored |
| `event.expiration_at_ms` | number | No | Used to set `subscriptionExpiresAt` on `CANCELLATION` and `EXPIRATION` |
| `event.original_transaction_id` | string | No | Used to set `subscriptionId` on `CANCELLATION` |

**Processing pipeline**

1. Returns `503` if `REVENUECAT_API_KEY`, `REVENUECAT_WEBHOOK_SECRET` or `REVENUECAT_APP_IDS` is not configured.
2. Returns `401` (generic body, no reason) if the `Authorization` header is missing or does not match `REVENUECAT_WEBHOOK_SECRET`.
3. Parses and validates the JSON payload against the webhook schema; returns `400` on malformed JSON or schema mismatch.
4. Returns `200` with `ignored: true` when `app_id` is not in `REVENUECAT_APP_IDS`, when the event type is not one of the four handled types, or when no local user matches `app_user_id`, `original_app_user_id`, or `aliases`.
5. For `INITIAL_PURCHASE` and `RENEWAL`, resynchronizes the user's active subscription from RevenueCat and sets `isPro: true`. For `RENEWAL` only (never `INITIAL_PURCHASE`, which is covered by the mobile app's own `purchase_completed` event), also sends a `subscription_renewed` PostHog event (see below) — only after the resynchronization succeeds. Since CP-1.1.1d, a failed resynchronization is handled:
   - **Temporary failure** (network error or timeout, any HTTP error from the RevenueCat API, missing configuration, database error): returns `503 webhooks/subscription-sync-unavailable` so RevenueCat retries the delivery. Nothing is written and no PostHog event is sent on that attempt; the renewal and its `subscription_renewed` event happen on the retry that succeeds (no duplicate event).
   - **Permanent failure** (`RevenueCatInvalidPurchaseError`: RevenueCat answered but has no active subscription of a known product for the user): returns `200` with `ignored: true`, so it is not retried forever. Nothing is written and no event is sent.
6. For `CANCELLATION`, attempts the same resynchronization first; if RevenueCat reports no active entitlement, records `subscriptionCancelRequestedAt` instead — `isPro` is not changed, so access is kept active until expiration. Also sends a `subscription_cancel_requested` PostHog event, unless the subscription was already inactive (see step 4's sibling early-return below).
7. For `EXPIRATION`, attempts the same resynchronization first in case a new subscription is already active; if none is found and the event's expiration timestamp has passed, sets `isPro: false`, clears `subscriptionCancelRequestedAt`, and sends a `subscription_expired` PostHog event.

**PostHog side effect.** All three events above use `String(user._id)` as the PostHog `distinctId` and include `{ product_id, store }` from the RevenueCat event. Sending to PostHog never affects this endpoint's response time or status code — `captureServerEvent` (`apps/api/src/services/analytics.service.ts`) is a no-op when `POSTHOG_API_KEY` is absent and never throws when it is present.

The endpoint returns `200` for every processed or ignored case so RevenueCat does not retry delivery. A non-2xx answer is used on purpose only when a retry can succeed: `503` for a temporary resynchronization failure on `INITIAL_PURCHASE`/`RENEWAL` (step 5), and `500` for an unexpected error on `EXPIRATION`. `REVENUECAT_API_KEY` itself was confirmed working end-to-end against the real RevenueCat API on 2026-11-01, after an earlier incompatible-key incident; see [`../fixes/posthog-analytics.md`](../fixes/posthog-analytics.md) for the full investigation and live verification.

**Success response**

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "processed": true,
    "eventId": "string",
    "eventType": "INITIAL_PURCHASE | RENEWAL | CANCELLATION | EXPIRATION"
  }
}
```

Ignored events also return `200 OK`, with a different payload:

```json
{
  "success": true,
  "data": {
    "ignored": true,
    "reason": "string"
  }
}
```

**Status codes**

| Status | Meaning |
|---|---|
| `200` | Event processed or intentionally ignored |
| `400` | Webhook payload failed schema validation |
| `401` | Missing or invalid `Authorization` header |
| `404` | Any path other than the exact `/webhooks/revenuecat/{REVENUECAT_WEBHOOK_PATH_SECRET}` |
| `503` | `REVENUECAT_API_KEY`, `REVENUECAT_WEBHOOK_SECRET` or `REVENUECAT_APP_IDS` is not configured, or (`webhooks/subscription-sync-unavailable`) a temporary failure resynchronizing an `INITIAL_PURCHASE`/`RENEWAL` — RevenueCat retries |

## Health

### GET /ping

Public health check endpoint used to confirm server availability and verify that a new Railway deploy is actually live.

**JWT required:** No

**Request parameters**

None.

**Success response**

**Status:** `200 OK`

```json
{
  "status": "ok",
  "version": "1.0.0",
  "environment": "development",
  "timestamp": "2026-04-29T12:34:56.000Z"
}
```

**Response fields**

| Field | Type | Description |
|---|---|---|
| `status` | string | Health indicator; current value is `ok` |
| `version` | string | API version from environment configuration; essential to confirm that a new Railway deploy was applied successfully |
| `environment` | string | Runtime environment such as `development`, `staging`, or `production` |
| `timestamp` | string | Current server time in ISO 8601 UTC format |

**Status codes**

| Status | Meaning |
|---|---|
| `200` | API is reachable and responding |

### GET /health

Readiness check endpoint. In addition to everything `/ping` returns, it includes the current MongoDB connection state, so a monitoring system can distinguish "process alive but database unreachable" from "process and database both healthy" — something `/ping` (always `200`) cannot express.

**JWT required:** No

**Request parameters**

None.

**Success response**

**Status:** `200 OK` when the database is connected, `503 Service Unavailable` otherwise.

```json
{
  "status": "ok",
  "version": "1.0.0",
  "environment": "development",
  "timestamp": "2026-04-29T12:34:56.000Z",
  "dbStatus": 1
}
```

**Response fields**

| Field | Type | Description |
|---|---|---|
| `status` | string | `ok` when the database is connected, `degraded` otherwise |
| `version` | string | API version from environment configuration |
| `environment` | string | Runtime environment such as `development`, `staging`, or `production` |
| `timestamp` | string | Current server time in ISO 8601 UTC format |
| `dbStatus` | number | Raw Mongoose `readyState` value: `0` disconnected, `1` connected, `2` connecting, `3` disconnecting |

**Status codes**

| Status | Meaning |
|---|---|
| `200` | API is reachable and the database connection is ready (`dbStatus: 1`) |
| `503` | API is reachable but the database connection is not ready |

## Error Response Format

### Standard Error Envelope

Most error responses follow this format:

```json
{
  "success": false,
  "code": "auth/invalid-credentials",
  "message": "Invalid email or password."
}
```

### Validation Errors

When a request fails Zod validation, the API returns `400 Bad Request` and includes an `errors` array describing each invalid field.

```json
{
  "success": false,
  "code": "validation/invalid-input",
  "message": "Validation failed.",
  "errors": [
    {
      "field": "email",
      "message": "errors.validation.email_invalid"
    },
    {
      "field": "password",
      "message": "errors.validation.too_short",
      "minimum": 8
    }
  ]
}
```

**Validation error fields**

| Field | Type | Description |
|---|---|---|
| `field` | string | Request field that failed validation |
| `message` | string | i18n key describing the validation failure |
| `minimum` | number | Present when the failure comes from a minimum constraint |
| `maximum` | number | Present when the failure comes from a maximum constraint |

### Development Diagnostics

Unhandled server errors pass through the global error middleware and may include a `stack` field when `NODE_ENV=development`.

```json
{
  "success": false,
  "code": "network/internal-server-error",
  "message": "Internal server error.",
  "stack": "Error: ..."
}
```
